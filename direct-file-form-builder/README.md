# Direct File

A static, multi-language tax questionnaire built as a Form Builder application. Flow XML describes
the questions, a fact dictionary describes the tax facts behind them, and `gov.irs::form-builder`
turns the two into a site: every page, in every language, as plain HTML under `./out`.

The questionnaire is a port of [IRS Direct File](https://github.com/IRS-Public/direct-file)'s
`df-client-app`. The Flow XML and `facts/flowGates.xml` are generated by the transpiler in
[`codemod/`](codemod/README.md) and are never hand-edited. The fact dictionary is a copy of Direct
File's, carried over unchanged. See [docs/PORTING.md](docs/PORTING.md) for what was ported, what was
left out, and why.

The site serves from `/app/direct-file`.

## What this is built on

| Library | Expected at | What it provides |
|---|---|---|
| `gov.irs::factgraph` | `../../fact-graph` | The fact evaluation engine, as a JVM jar and a Scala.js browser bundle. |
| `gov.irs::form-builder` | `../../form-builder` | The scaffold: flow parser, site generators, Thymeleaf engine, node templates, chrome locales, the theme, and the browser flow runtime. |
| `taxpert` | `../../taxpert/packages/ui` | The workspace laid over the running app: global nav, audit panel, and the Inspect, Outcome tracker and Watchlist tool panels. Optional, and this app was generated with it. |

Each is resolved from a local checkout rather than a package registry, so this app expects each at
the path above. If a library moves, update the path in `Makefile`, `package.json`, `Dockerfile`,
`docker-compose.yml` and `docker-compose.override.yml`.

The layout this app assumes:

```
parent/
├── fact-graph/
├── form-builder/
├── taxpert/
│   └── packages/ui/    the workspace package this app depends on
└── form-builder-examples/
    └── direct-file-form-builder/
```

The transpiler additionally needs a Direct File checkout, at `../../direct-file` by default. Set
`DF_CLIENT_APP` to point elsewhere. Nothing in this repository writes to it.

## Requirements

JDK 21, sbt, Node 22, and `xmllint` for the XML validators (`libxml2-utils` on Debian or Ubuntu).
`make smoke` also needs a Chromium download, which `npx playwright install chromium` fetches once.

`build.sbt` names one dependency, `gov.irs %% "form-builder"`, and declares no resolvers. That
library and the `gov.irs::factgraph` it pulls in transitively are resolved from the local Ivy cache
at `~/.ivy2/local`, so each has to be published there once from its own checkout. Neither is
published to a remote registry. `make bootstrap` does the publishing for you.

## Getting started

```bash
make up           # http://localhost:3008/app/direct-file/
```

That needs no JDK, sbt or Node. It builds the sibling libraries, generates the site, serves it, and
leaves an `sbt ~run` watcher regenerating on every edit. Four surfaces come up together:

| Surface | Address | Served by |
|---|---|---|
| The flow | `http://localhost:3008/app/direct-file/` | this stack's nginx |
| Browse All | `http://localhost:3008/app/direct-file/all-screens/` | this stack's nginx |
| Author Mode | `http://localhost:3008/app/direct-file/author/` | this stack, with its API on `127.0.0.1:3009` |
| Fact Explorer | `http://localhost:5180/fact-explorer/direct-file` | the taxpert stack |

Author Mode's API writes to `flow/*.xml` and `facts/*.xml` in this working tree, which is why it is
published on `127.0.0.1` rather than on every interface. The watcher regenerates the site from those
edits, so a save in the browser becomes a changed page a moment later.

Fact Explorer belongs to the taxpert stack rather than this one. It holds every application at once,
so there is one instance beside them all. `make up` writes a bind mount for this repository into
`../../taxpert/docker-compose.apps.d/` and starts it. See `scripts/register-with-taxpert.sh`, and
run `make unregister-explorer` before you move or delete this repository. A symlink into
`taxpert/apps/` does not work, because a bind mount carries the link rather than its target.

To run natively instead:

```bash
make bootstrap    # once: publish the libraries, install deps, vendor their assets
make dev          # same address, without Author Mode
```

## Commands

`make help` lists every target. The ones you are likely to need:

| Target | What it does |
|---|---|
| `make dev` | Dev server with the workspace, Browse All and Scenario mode, watching for changes. |
| `make dev-topic-pages` | The same, showing the un-split flow: one page per Direct File SubSubcategory. |
| `make dev-author` | The same as `dev`, plus Author Mode on port 3009. Deliberately un-split. |
| `make debug` | The same as `dev`, with a JVM debug port on 5005. |
| `make site` | The production build into `./out`. |
| `make test` | ScalaTest, plus a scalafmt check. `make test-watch` for the watching version. |
| `make smoke` | The browser smoke test over `./out`. Needs `make site` first. |
| `make ci` | Build, then every validator in turn. `make ci-setup` installs what the validators need. |
| `make format` | Format the Scala and the JavaScript. It leaves the XML alone, see Gotchas. |
| `make clean` | Delete `target/`, `project/*/target/` and `out/`. |
| `make diff-out` | Build `main` in a throwaway worktree and diff the two `out/` trees. Useful for any change meant to be output-neutral. |
| `make fact-explorer` | Build with `--formBuilderGraph` and print this app's Fact Explorer URL. |
| `make transpile` | Regenerate the flow and its gate facts from Direct File. |
| `make transpile-verify` | Check the port against Direct File: page order, then gate parity per scenario. |
| `make export-scenarios` | Regenerate the scenario corpus from Direct File's backend fixtures. |
| `make up` `down` `logs` `ps` `rebuild` | The Docker stack. `rebuild` is the escape hatch for a stale sibling library. |
| `make register-explorer` `unregister-explorer` | Add or remove this app's mount in the taxpert stack's Fact Explorer. `up` runs the first for you. |

`copy-fg`, `copy-shared-ui` and `copy-uswds` regenerate the vendored mirrors under
`website-static/vendor/`. Every build target runs them first, so you rarely call one by hand.

Ports are `PORT ?= 3008` for the site, `AUTHOR_PORT ?= 3009` for the Author Mode API, and
`DEBUGGER_PORT ?= 5005`. Override any of them on the command line.

### One question per screen

Every build target except `dev-topic-pages` and `dev-author` passes `--singleQuestionPerScreen`,
which is the opposite of the other three applications in this repository. The transpiler collapses
Direct File's 727 screens into 138 topic pages, one per SubSubcategory, with in-page conditions
hiding what does not apply. At that grain a single page can carry dozens of questions. Split back
apart it is 378 pages, each one upstream screen, which is the shape Direct File ships.

`make dev-topic-pages` shows the un-split flow, which is the level to look at when a question appears
on the wrong page. Author Mode stays un-split because it edits the XML on disk, and the splitter's
pages are not on disk.

CI lives at the repository root in `.github/workflows/quality-checks.yml`. There is no `.github/`
directory here. It runs the four validators (`validate-xml`, `validate-templates`, `validate-js`, `validate-scala`) for
each of the four applications. It does not run `make site`, `make test` or `make smoke`.

The application itself:

```
src/main/scala/gov/irs/directfile/
├── Main.scala      the FormBuilderApp value and one call to FormBuilder.run
└── inputs/         the four parsers behind this app's eight custom input types

src/test/scala/gov/irs/directfile/
├── FlowSpec.scala           the flow parses, and the shape the transpiler promises
└── DeterminationSpec.scala  the fact dictionary computes Direct File's arithmetic

src/main/resources/direct-file/
├── flow/           GENERATED. index.xml names the modules, and each <page> becomes a directory
├── facts/          the fact dictionary. 36 modules copied from Direct File, plus flowGates.xml
├── locales/        this app's strings. flow_*.yaml are GENERATED from the flow
├── templates/      only what this app overrides. Everything else comes from the scaffold
├── scenarios/      161 saved fact graphs the Scenario modal offers

└── website-static/ served verbatim at /resources: styles, js, img, and the vendored mirrors
```

### Flow XML

`flow/index.xml` names each module with `<module src="…"/>`, and the scaffold splices them together
before parsing. A `<page route="…">` becomes a directory in the built site, and routes must be unique
across the whole flow. Inside a page you have `<section>`, `<fg-set path="/someFact">` with a
`<question>` and an `<input type="…">`, `<fg-alert>`, `<fg-detail>`, `<fg-collection>`,
`<modal-dialog>` with `<modal-link>`, and ordinary HTML for prose.

Authored text lives here rather than in a locale file. Every question, hint and alert heading is
extracted into `locales/flow_en.yaml` on every build.

This directory is transpiler output. To change a page, change the transpiler and run `make transpile`.

### Facts

`facts/*.xml` hold the `<Fact path="…">` definitions. `<Writable>` is something a taxpayer answers
and `<Derived>` is something computed from other facts. Every file in the directory is loaded in
sorted filename order and merged into one dictionary, and on a duplicate path the last definition
wins.

36 of the 37 modules are Direct File's, carried over unchanged. The 37th is `flowGates.xml`, which
holds the 798 Boolean facts the transpiler synthesizes from Direct File's screen conditions, plus
`/flowAlwaysTrue`.

The facts are validated against `facts/FactDictionaryModule.rng` and the flow against
`flow/FlowConfig.rng`. Both schemas belong to this app, so widen them when you widen the flow.

A fact path in the flow that does not resolve in the dictionary fails the build, and `FlowSpec` is
what catches it.

### Locales

`locales/en.yaml` and `locales/es.yaml` carry this app's own words, layered over the chrome strings
the scaffold ships. Lookup is app first, then the library, then the generated flow locale, so
declaring a key the scaffold also has overrides it without copying the rest.

One key per flow module lives under `all-screens.section.*`. These supply the section headings on
the Browse All listing and the labels on the step indicator. `make transpile` refuses to write
unless all 25 are present.

`locales/flow_en.yaml` and `locales/flow_es.yaml` are generated from the flow XML. `flow_es.yaml`
currently holds 15 lines, so the Spanish pages build and render English text under Spanish chrome.
That is the port's largest remaining gap, and docs/PORTING.md explains why it is a post-build step.
Editing `flow_en.yaml` by hand loses the edit at the next build.

### Brand CSS

`website-static/styles/main.css` imports USWDS, then the Form Builder theme, then this app's own
`components/brand.css`. Put overrides in `brand.css` or below the theme import, where they win by
ordinary cascade order. Do not fork a theme file to change one value.

`brand.css` carries no declarations today, only the cookiecutter's commented example. The theme is
USWDS and so is Direct File, so there is no token this application needs to re-tint.

### The workspace mounts

`templates/fragments/` holds four fragments the library ships empty and this app fills in:

| Fragment | Fills in |
|---|---|
| `workspace-head.html` | the stylesheets and element modules |
| `workspace-enable.html` | the call that turns the workspace on, and the Scenario picker's filters |
| `workspace-all-screens.html` | the screens toolbar |
| `taxpert-config.html` | the nav taxonomy, the determinations, the endpoints |

Only these fragments name a path inside `vendor/taxpert/`, which is what keeps the library free of
any reference to a package an application can drop.

`templates/fragments/usa-step-indicator.html` is a fifth fragment, and it overrides one the library
does ship. It renders one segment per flow module rather than one per page. See docs/PORTING.md.

The code those fragments call, meaning the fact-graph port and the fact paths the outcomes are built
from, lives in `website-static/js/taxpert/direct-file-graph.js`. Labels go through Thymeleaf and are
resolved per locale at build time, while `website-static/` is served verbatim and never passes
through Thymeleaf, so a string written there would be English in the Spanish build.

## What checks what

Four gates, answering different questions.

| Gate | Command | Answers |
|---|---|---|
| Parity | `make transpile-verify` | Does this flow show each screen to exactly the taxpayers Direct File shows it to? Needs a Direct File checkout. |
| Dictionary | `make test` | Does the fact dictionary still compute Direct File's arithmetic, and does the flow still have the shape the transpiler promises? |
| Build | `make ci` | Does it generate, validate and lint? |
| Browser | `make smoke` | Does the generated site run? |

`make smoke` is the only one that opens a browser, and it covers a class of failure the others
cannot see. The parity gates compare `Condition.evaluate` against the synthesized gate facts
in-engine and never render a page, so they are blind to a fact path the browser cannot write, an
input type that fails to register, or a module that throws at import. Both have happened here. 47
questions threw `requirement failed` until `seed-fact-graph.js` created the second filer, and three
input modules threw out of `connectedCallback` on any page holding an unanswered address or TIN.
Neither moved a single number in the parity run.

The smoke test is deliberately small: the first few pages, one scenario, seven assertions.
`codemod/verify-visibility.ts` is where the question "which screen shows for whom" belongs. See
`tests/smoke.spec.js`.

```bash
make site && make smoke          # it reads ./out, so the build has to exist
npx playwright install chromium  # once, on a machine that has not run Playwright before
```

## Three rules to follow

1. **Authored text goes in the flow XML**, and the flow XML is generated. `locales/flow_*.yaml` are
   build outputs, and so is everything under `flow/`. Corrections go into `codemod/`.
2. **Never hand-edit anything under `website-static/vendor/`.** Every directory in there is a
   generated mirror with exactly one writer: `make copy-uswds` for USWDS, `make copy-fg` for the
   Scala.js fact graph, `make copy-shared-ui` for taxpert, and the scaffold itself for
   `vendor/form-builder/`, which it extracts from its own jar as it generates the site.
   `make check-shared-ui` fails the build if the taxpert mirror drifts.
3. **Override rather than fork.** Change a node template by dropping a same-named file into
   `templates/nodes/`, since app templates resolve ahead of the library's. Change a chrome string by
   declaring that key in `locales/en.yaml`.

## Extending the scaffold

Two seams, both registrations on the `FormBuilderApp` in `Main.scala` rather than edits to the
library:

- **`nodeTypes`** maps a flow element the scaffold has never heard of to a `FlowNodeParser`. Put the
  element's Thymeleaf template in `templates/nodes/`, and widen `flow/FlowConfig.rng` to allow it.
  Mirror the tag name in `customFlowTags` in `fact-explorer.app.json`, or Fact Explorer rejects it.
  This application registers none.
- **`inputTypes`** maps an `<input type="…">` value to an `InputParser`. Registering an existing name
  replaces the built-in rather than adding a second one.

This application registers eight input types from four parsers in `src/main/scala/gov/irs/directfile/inputs/`:

| Type | Parser | Fact Graph node |
|---|---|---|
| `tin` `ein` `pin` `ip-pin` `phone-number` | `MaskedNumber.scala` | `TinNode`, `EinNode`, `PinNode`, `IpPinNode`, `PhoneNumberNode` |
| `address` | `Address.scala` | `AddressNode` |
| `bank-account` | `BankAccount.scala` | `BankAccountNode` |
| `collection-item-reference` | `CollectionItemReference.scala` | `CollectionItemNode` |

Each name selects three things that have to agree: the parser, `templates/nodes/inputs/{name}.html`,
and the handlers registered under it in `website-static/js/inputs/`.

## Deciding where a change goes

| The change is about | It belongs in |
|---|---|
| A page, a question, a word a taxpayer reads | `codemod/`, then `make transpile` |
| A fact, a rule, a threshold | `facts/`, and upstream Direct File if it is a real tax-logic change |
| How any Flow XML becomes HTML: the parser, a generator, a node template, a chrome string, the theme, the flow runtime | `../../form-builder` |
| The workspace: nav, audit panel, Inspect, Outcome tracker, Watchlist | `../../taxpert/packages/ui` |

A change in a library needs `sbt test publishLocal` (or `npm test`) there, and then a `make ci` in
every application built on it. A second application is what catches an assumption that only holds
for the first.

## Gotchas

- **An incomplete fact has no value at all.** A derived fact over an unanswered input returns `None`
  rather than `false`. Code that collapses the two will tell a taxpayer they do not qualify when the
  honest answer is that we have not asked yet. On the browser side, `Result.get` throws on an
  incomplete result, so read `fact.complete` before `fact.get`.
- **`make format` does not touch the XML here**, unlike the other three applications. `facts/` is
  Direct File's dictionary carried over unchanged, and `xmllint --format` rewrites all 36 modules
  and destroys the byte-for-byte correspondence that makes the copy auditable. `flow/` is generated,
  so formatting it is undone by the next `make transpile`.
- **`make validate-templates`** rejects HTML comments inside inline `<script>` blocks. They are legal
  in a classic script and a syntax error in a module, and nothing else in the build catches it.
- **Both RELAX NG schemas are yours.** `make validate-xml` runs the facts half and the flow half. A
  schema that is never widened alongside the flow it describes drifts out of agreement with it.
- **`make validate-html`'s glob does not reach the whole `out/` tree.** The same content reports 20
  warnings at 139 pages and 79 at 378. The warnings are real, and the coverage is the bug.
- **`make ci` fails intermittently on a shared `target/`.** The dev overlay's watch container
  bind-mounts this repository and runs `sbt ~run` inside it, so a containerised build and a host
  build share one `target/scala-3.7.2/classes`. Run `make down` before a host build. `build.sbt`
  carries the full diagnosis.
- **`make diff-out` needs a commit on `main`.** A freshly generated repository has everything staged
  and nothing committed, so make the first commit before expecting a diff.
