Both should be 0. The first is the join's own failure mode, a screen whose Spanish resolves to a
differently-shaped tree; the second means one language resolved a screen the other did not, which
upstream's own locale parity should make impossible. A page in `flow_en.yaml` that `pages.json`
does not have is not counted here at all — it means the two were built from different runs, and it
fails by name rather than writing a file that is missing a page.

## Two things that look like defects and are not

**204 values are one English sentence with two translations.** Direct File writes
the same sentence under two keys — a screen and a modal, or two phrasings of the same aside — and
translates each in its own words: "¿Qué es un PIN para la Protección de la Identidad (IP PIN)?" and
"¿Qué es un IP PIN?" for one English question. There is one key here to put either under, because
form-builder content-addresses on the English and has already collapsed the two, so the first
occurrence on the page wins. Not a choice this stage makes that the library does not.

**16 values interpolate different facts in the two languages.** Upstream writes "hasta el 15
de abril de {{/nextTaxYear}}" where its English says "for {{/lastTaxYear}}", and drops a name where
Spanish repeats the noun instead. `verify-translation.ts` is what makes that safe to accept: every
path either language names is checked against the dictionary, and every modal against the dialogs
its own page carries.
